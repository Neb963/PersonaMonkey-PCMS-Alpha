# PersonaMonkey-PCMS Alpha — normative product and technical specification

**Status:** proposed design; no implementation or provider-live acceptance is claimed. **Product:** `Neb963/PersonaMonkey-PCMS-Alpha` (new public derivative repository). **Generator source:** `Neb963/per-gens` (one private repository). **Target:** one Fedora computer, one Firefox profile, one installed unsigned/private-use combined extension; no multiple hosts or browser instances controlling the same accounts.

## 1. Objective and non-goals

A dependable Perchance generator fleet manager for ~50+ accounts and potentially 1,000+ generators. Optimize unattended bulk reservation, approved deployment and visibility management, not manipulation of individual generators in everyday use. Keep the operator-facing product small, native-feeling and unambiguous.

**Four built-in product areas, not runtime plugins:** Accounts; Generator Inventory & Management; Supply/Deployer; Refresher. Notifications, compact statistics, recovery, settings and backup are shared services/views. Remove the runtime-installable module/package authority, generalized module UI contribution framework, Explorer as independent subsystem, Statistics as independent module, cohort model, and generalized workflow/scheduler abstractions not needed by Alpha. Do **not** remove the durable correctness guarantees those systems happened to implement.

Not in Alpha: new AI provider or local LLM runtime; generic module marketplace; browser execution duplicated outside PersonaMonkey; CAPTCHA solving/bypass; server-side control plane; automatic generator renaming; speculative Perchance endpoints or permanent browser tabs per generator; migrated legacy PCMS data.

## 2. Ownership and architecture

**One XPI, two code domains.** PersonaMonkey owns Personas (`personaUid`), contextual identity/cookie isolation, routing/Mullvad and fail-closed guards, browser execution and control leases, its persistent state and compatibility. Alpha's background-authoritative Core uses a typed internal Persona Broker with the same semantics as PersonaMonkey Integration API v1. Alpha does not call PersonaMonkey internals, raw native RPC, or create a second browser userscript/workflow engine. Preserve PersonaMonkey's internals at first; simplify exposed navigation. Unused subsystems may be removed only after dependency tests prove safety.

Alpha Core owns durable local IndexedDB state, generation/revision fences, external operation ledger, recovery hold, periodic alarms, bounded task/tab allocation, notification queue and backup coordination. UI tabs/popup are clients and do not run Core. Firefox background event-page unloading must not suspend scheduling authority or erase operations. No reliance on event-page memory persistence, synthetic keepalives, DevTools MCP or Chromium behavior.

Feature services are static imports, not installable modules. Keep their contracts small and typed. Single authoritative **Generator** identity combines `slug`, owning Account ID, `personaUid` binding reference, managed/excluded intent, listing observation, deployment release provenance, operational state, and refresh schedule, but these remain independent facts; do not collapse them into a single mutable `status` field.

Core facts: Account and Persona binding; generator slug and owner; publication state (`UNLISTED`, `PUBLIC`, `UNKNOWN`); fleet inclusion (`MANAGED`, `EXCLUDED`); deployment lifecycle; refresh lifecycle; last confirmed source/release hash; repo path/commit; current operation; timestamps/observations; attention state. Public, eligible, deployed and active are **not synonyms**. Reserved undeployed generators are unlisted and excluded from refresh; imported existing generators are excluded until manually enrolled.

## 3. Account enrollment

Wizard: create Persona through PersonaMonkey; open clean account tab; if Cloudflare/session problem, offer manual route selection via PersonaMonkey and open a clean retry tab while closing only Alpha-owned attempt tabs; operator logs in manually; operator marks done; verify session identity in Perchance page context; bind Account ↔ `personaUid` durably; discover owned generators and states through authorized account-scoped observation; show Persona/route, account name, email if obtainable, generator count, session condition and attention. One-time manual entry is permitted for undiscoverable fields. Session challenges and CAPTCHA always require the operator, with no automation bypass. One active account ↔ one dedicated Persona; controlled rebinding previews affected generators/unresolved work and increments binding generation.

## 4. Generator inventory and supply

Operator pastes arbitrary candidate slug list. For each: validate syntax, check availability/ownership, allocate eligible accounts as evenly as feasible **for new reservations**, create real unlisted empty generator in account Persona, confirm ownership, create corresponding GitHub generator folder with `DEPLOYMENT.md` in BLOCKED state. A GitHub directory without a file cannot exist: the status document is its initial committed content. Track multi-system progress durably so Perchance success/GitHub failure is repaired without creating duplicate slugs. Never claim exclusive ownership from a local availability check alone; provider creation/confirmation is the authority. Partial reservation may wait for GitHub reconciliation.

Supply also supports existing READY GitHub folders: resolve folder/slug mapping, reserve/create if needed, and proceed to deployment when eligible. Default folder path is `generators/<slug>/`, configurable path templates under one configured repository. No arbitrary regular-expression replacement or global manifest is required. The repository may contain unrelated docs/subfolders: Alpha reads only readiness and the configured deployment files. Reservation count is unbounded by the original illustrative 200; provider and quota limits are observed, not invented. Account balancing applies **to reservation**, not to refresher scheduling.

## 5. `per-gens` integration contract

One private GitHub repo. Minimal layout: `generators/<folder>/DEPLOYMENT.md`, `main.pjs`, `index.html`, `thumbnail.jpeg` (the thumbnail may be configured but required for a deployable package unless proven optional). Other files are ignored. The status file has exactly one machine-parseable line `Status: BLOCKED | IN_DEVELOPMENT | READY`, with optional human notes. Missing/ambiguous/unrecognized status means blocked. Newly created folder starts BLOCKED. The generator coding agent develops in `generator/<slug>` branch, passes its checks, then merges READY and the files into `main`. `READY` stays READY across future revisions; a new *deployable content hash* triggers deployment, not a status or documentation-only change. Folder slug and Perchance slug may differ through an explicit per-generator binding, not silent inference.

GitHub connectivity uses a narrowly scoped Contents read/write credential for only the configured repository, stored through the existing approved secret host, never logs/normal DB. A source snapshot is pinned to an exact commit, individual blob identities and canonical SHA-256 of deployable bytes. Read/write source from `main` only; do not access agent development branches. Live AI corrections write `main.pjs` and/or `index.html` together in **one atomic Git commit** with message such as `Fix live deployment: <slug>`; do not commit refresher-only comments, secret material or unrelated documents. The write uses compare-and-swap/branch-head precondition; an intervening developer merge halts writeback for reconciliation, never force-pushes or overwrites. PCMS records the resulting Git commit/release so it does not trigger a deployment loop.

## 6. Deployment pipeline and AI helper

On each configurable periodic scan, inspect READY generator folders. New READY content is copied/saved automatically into its reserved unlisted Perchance generator through the owning Persona. Every external change first creates a durable operation identity and verifies target ownership/session, source hash, and expected provider source revision. Only **sleeping or never-active** generators are eligible for Deployer mutations; active generators are never updated, including urgent fixes. Active-generator update jobs wait until the next sleep transition.

New generator: staged unlisted save → verify exact PJS/HTML/thumbnail and source revision → queue native Perchance AI-helper test+fix session. AI concurrency is configurable globally per account, default one session/account; session slots are released after AI completes and saves a durable review record, even while human approval is pending. Use a small bounded tab budget; close only program-owned tabs; never close user-owned editor tabs. Session recovery, rate limits, reconnects and CAPTCHA become explicit attention states. An AI helper test prompt requires short functional tests, corrective changes and human-readable code comments explaining modifications. Do not treat untrusted AI output as verified code.

Manual approval happens on `/<slug>#edit` with a compact context overlay. **Mark ready** ensures Perchance save completes, reads back and confirms exact code, rejects unresolved/stale GitHub states, atomically writes any human-approved AI fixes to GitHub, records the new release, switches public, confirms the listing operation, then marks managed/eligible for Refresher. Approval does not allocate an active slot immediately. Before approval, remain unlisted.

Updated deployed generator: wait until sleep; set unlisted and confirm; apply updated READY content; test with AI and wait for approval; republish and return to eligible sleep queue. When an update fails, restore last confirmed known-good version if the provider state can be safely reconciled; **leave unlisted, sleeping and visibly flagged** until reviewed. Do not repeatedly deploy the same failed Git revision; a newer content hash or explicit manual retry is required. A new generator that fails AI may try bounded fresh conversations; on exhaustion leave unlisted and flagged. If uncertain, stop and reconcile before any retry. Detect any unexpected live source drift; pause mutation and request operator reconciliation. Operator may explicitly **Ignore this detected change** for the currently observed revision, with logged scope; do not treat this as blanket future auto-overwrite.

## 7. Refresher and listing visibility

The Refresher is one service with one simple mode. Global UI settings: active period A (default 24h), minimum sleep S (example 72h), optional manual active cap override, listing margin (example 10%). Internally jitter A/S transitions within ±30 min, bounded so it does not violate minimum sleep; not exposed as separate UI complexity. Each eligible generator is independently tracked with start/end, accumulated **healthy operational active time**, last confirmed refresh, last observation and next eligibility. Browser shutdown and confirmed Perchance outage pause active accumulation. Normal Firefox background event-page idle/unload does not pause; use persisted checkpoints, alarms and bounded healthy intervals. Resume safely after restart without unbounded timer replay.

Automatic target active cap is derived from current managed eligible population and A/(A+S), and bounded by empirically observed recent-page capacity and configured margin. User can override within safe bounds. This is a target, not a claim of 283 hard slots or guaranteed ranking. If demand exceeds capacity, choose the longest-sleeping eligible generator; sleep is minimum, never an entitlement to immediate activation. Manual pull-out/pull-in changes queue eligibility without mutating deployed content or resetting unrelated generators; manual removal is durable and never instantly resurrected by timer.

Every 10 minutes, obtain recent-feed data and assess **actual rendered presence/position** under page-specific ordering/filtering (pinned entries, exclusions). Position target is top `ceil(activeCount × (1+margin))`. If active, public, eligible generator is absent/below target, perform a bounded refresh attempt with non-simultaneous staggering and retry after a controlled page reload when appropriate. Per user requirement, a refresh consists of a harmless small edit/comment and save in one source pane; store its exact insertion and previous bytes durably so the next edit can replace that exact comment. Do not let these transient edits change canonical release hashes or GitHub writeback. Verify save, source continuity, and position, and respect rate limits/provider behavior. A mere successful save does not establish public visibility. The supplied `/generators` source includes explicit filtering of repeated trivial-save behavior; when filtering or failure persists, slow retries, alert, then suspend that generator rather than spam indefinite saves.

10-minute recent-list observation is global, not 1,000 account-specific page loads. Collect per-generator view statistics adaptively: frequent enough for meaningful daily/weekly deltas, slower for sleepers, excluded, old and low-priority generators. Maintain bounded history aggregates; report stale timestamps and unknown fields honestly. Do not assume `getGeneratorList` lists every owned generator; account-scoped discovery is separate. Absent from public feed ≠ proven ban. Show `not visible`, `likely filtered` or `confirmed prohibited` only with corresponding evidence.

## 8. Generator management, UI and notifications

The principal UI is a full Firefox tab, with a small toolbar status and Perchance editor overlay. Simple static navigation: Overview, Supply & Deployments, Refresher, Accounts, Generators, Attention, Settings. Overview prioritizes counts, backlog, health and actions rather than diagnostics. Most operations are bulk; individual generator detail appears via search, filter, drill-down, or attention. Generator quick actions: public/unlisted (when permitted), managed/excluded, update from GitHub (queue only if active), inspect code/source drift, open edit Persona, retry failed job, export record, delete with impact preview and typing `yes`. No generator rename in Alpha. Deletion affects Perchance only; retains recoverable tombstone/history, never silently deletes GitHub source. Distinguish UI commands from actually confirmed provider states. Desktop + in-app notifications for actions needing attention/serious errors; aggregate routine successes and deduplicate noisy retries. Native-feeling density, clear typography, keyboard and focus semantics, no decorative animation/floating panels beyond necessary editor overlay/dialog, dark/light support and meaningful loading/error/empty states. 1,000 rows are virtualized/paginated, not all rendered simultaneously.

## 9. Durable operations, recovery and backups

Before any GitHub or Perchance mutation write an immutable target/revision-aware operation record; if the outcome is ambiguous mark UNCERTAIN, enter scoped hold and read authoritative remote state before retry. PersonaMonkey execution authority and local durable operation identity are both required where applicable. Revision, account binding generation and provider compatibility fence stale workers. Never blindly replay possibly committed writes. Use a bounded operation journal and explicit retention, no unbounded workflow engine.

One **unencrypted** backup file, on operator's explicit informed choice, combining Alpha DB/journal/settings, PersonaMonkey exportable state, Personas/routes and available sensitive session/secret material; do not claim to export credentials or sessions APIs cannot expose. Never upload backup to GitHub/CI or print secrets to logs. Daily backup to `Downloads/<Alpha-backups>/`, manual export and staged restore with schema/checksum verification, preview and `RECOVERY_HOLD`; apply atomically where possible and reconcile provider/binding/session after restore. Keep bounded known-download retention; if Firefox cannot identify/remove an older downloaded file, show cleanup warning. Do not silently claim perfect filesystem retention or session reusability. An interrupted backup never replaces last known good.

## 10. Acceptance and failure matrix

Required deterministic evidence: clean install and two-dashboard-tab authority; background idle/restart/alarms; 50+ account projections; 1,000-generator inventory/schedule performance; slug collision and partially completed GitHub+Perchance reservation; missing/blocked READY file; GitHub concurrent branch update / denied token / rate limit; update delayed until sleep; AI per-account concurrency and pending-review release; stale editor state/save/readback; rollback/unlisted/sleep on failed update; transient refresh comments excluded from content hashes; pinned/filtered recent-page fixture; outage/shutdown healthy-active ledger; suspension after bounded failures; session/Cloudflare challenges without bypass; route failure fail-closed; complete backup/export/checksum/restart/reconcile and inability to delete unknown downloads; notification deduplication; tab budget; no plaintext credentials in repo, logs, CI or screenshots; keyboard UI and 1k-list rendering; packaged XPI Firefox regression.

Provider-dependent mutation and session tests must use emulator/fixtures and pinned packaged Firefox in CI, then operator-run manual live acceptance only at the final gate. Any disagreement must be captured as deterministic fixture before a fix. **No green CI result alone means provider-live acceptance.**

## 11. Outstanding evidence, not unresolved product decisions

- Exact current Firefox Development/ESR API and signed/unsigned-install constraints, provider compatibility, Perchance AI helper page lifecycle, direct endpoint availability and rate limits must be checked in pinned Firefox. Source discovery was observed in Brave and is not proof of Firefox behavior.
- Actual public-list capacity and its filter logic are mutable third-party behavior; cannot promise perpetual top-placement.
- Backup contents depend on PersonaMonkey's real serialization/export authority and native config availability; use a truth table of restorable/not-restorable artifacts before advertising complete recovery.
- The design is approved only after the user reviews it; this package is **documentation and prompts, not implementation**.
