# PersonaMonkey v0.8.0 — PCMS Control Plane Context

## Status and purpose

This is the implementation contract for **v0.8.0 — PCMS Control Plane
Foundation**. It records the shipped architectural boundary; implementation
and the stable protocol documentation in `docs/PCMS_API.md` remain synchronized
with this document.

The baseline is **v0.7.4** and the shipped product/package version is
**0.8.0**. `main` is the canonical source branch, and v0.8 work belongs on a
short-lived branch from current `main` (normally `feat/v0.8-pcms-foundation`).
The repository root is the live source tree; historical
`persona-mullvad-router-v0.3.0/` layouts are not an alternative source tree.

PCMS is a management client of the Persona OS, never a second privileged
implementation layer.

```text
PCMS console/client
        |
        v
PCMS control plane v1 (commands, capabilities, batches, events)
        |
        v
Persona OS facade
  PersonaManager / StorageManager / WorkflowRunner / Diagnostics / RouteManager
        |
        v
Persona platform, workflow orchestrator, routing and Firefox APIs
```

## Baseline and compatibility boundary

v0.7.4 already provides Persona lifecycle operations, contextual-identity
backed storage inspection and clearing, container rotation for true wipes,
portable `.personamonkey` packages, the workflow orchestrator, diagnostics,
routing policy, privacy enforcement, and the narrow `PERSONA_API` facade.
The existing facade remains the foundation. PCMS must extend it additively and
must not replace it.

In particular, v0.8 must retain all existing release invariants:

- Gecko extension ID `persona-route-manager@local` and readable persisted state
  (current state schema is `SCHEMA_VERSION = 2`);
- fail-closed routing, with Block as the safe/default route and Direct only by
  explicit choice;
- strict proxy verification, privacy-control enforcement, First Party
  Isolation, and partitioned-cookie semantics;
- cookie and site-data operations scoped to the exact managed persona
  `cookieStoreId`, and full wipe as contextual-identity rotation rather than a
  broad browsing-data deletion;
- non-sensitive defaults for Persona packages and a separate encrypted full
  backup contract;
- existing userscript/workflow validation, ownership, cancellation, and tab
  cleanup boundaries; and
- no credential, WireGuard private material, cookie value, session token, GM
  storage value, or raw browser-profile data in PCMS status, route inventory,
  diagnostics, or events.

PCMS callers must not receive raw `browser.*` capability and must not get an
arbitrary `SAVE_STATE`, dynamic namespace/method invocation, or native-host
RPC capability. `native/native_host.py` remains the narrowly scoped Mullvad
bridge.

## Protocol v1

The implementation exports `PCMS_PROTOCOL_VERSION = 1`. PCMS requests are
bounded JSON envelopes sent through extension-internal runtime messaging:

```js
{
  type: "PCMS_REQUEST",
  version: 1,
  requestId: "caller-generated-id",
  command: "persona.list",
  params: {}
}
```

`requestId` is echoed unchanged and is useful for client correlation; it is not
an authorization mechanism. The control plane rejects malformed envelopes,
unsupported versions, unknown commands, and invalid parameters before calling
a service. The initial hard maximum serialized request size is **1 MiB**.

Successful responses have a stable envelope:

```js
{
  version: 1,
  requestId: "caller-generated-id",
  ok: true,
  bootId: "runtime-unique-id",
  revision: 42,
  result: {}
}
```

Failures use the same correlation, boot, and revision fields:

```js
{
  version: 1,
  requestId: "caller-generated-id",
  ok: false,
  bootId: "runtime-unique-id",
  revision: 42,
  error: {
    code: "PERSONA_NOT_FOUND",
    message: "Managed persona not found",
    retryable: false,
    details: null
  }
}
```

Thrown stack traces and raw internal exception objects are never serialized.
`details` is optional bounded, secret-safe context; clients must branch on
`code`, not message text. Expected errors are normalized at the protocol
boundary. Unexpected failures become `INTERNAL_ERROR` with a generic message;
implementation logging may retain non-secret diagnostic context locally.

The initial stable code set is:

| Code | Meaning |
| --- | --- |
| `PCMS_PROTOCOL_UNSUPPORTED` | Request version is not supported. |
| `PCMS_BAD_REQUEST` | Envelope or parameters are malformed or exceed bounds. |
| `PCMS_UNKNOWN_COMMAND` | Command is not explicitly registered. |
| `PCMS_CAPABILITY_UNAVAILABLE` | Supported protocol lacks a currently available service. |
| `STATE_CONFLICT` | `expectedRevision` did not match the current runtime revision. |
| `PERSONA_NOT_FOUND` / `PERSONA_UNMANAGED` | Target is absent or not a managed persona. |
| `ROUTE_NOT_FOUND` / `ROUTE_DISABLED` | Route cannot be selected safely. |
| `DIRECT_ROUTE_REQUIRES_OPT_IN` | Direct assignment omitted `allowDirect: true`. |
| `WORKFLOW_NOT_FOUND` / `JOB_NOT_FOUND` | Workflow or public job target is absent. |
| `BATCH_COMMAND_NOT_ALLOWED` / `BATCH_LIMIT_EXCEEDED` | Batch command or batch bounds are invalid. |
| `BATCH_CANCELLED` | A `failFast` batch item was not started after an earlier failure. |
| `DESTRUCTIVE_CONFIRMATION_REQUIRED` | Explicit destructive intent was required but absent. |
| `INTERNAL_ERROR` | Unexpected, non-leaking implementation failure. |

## Capability discovery and command registry

`system.describe` is mandatory and reports the actual installed capability
set, rather than an aspirational one. Its result includes product and protocol
versions, the imported state-schema constant, `bootId`, current `revision`, and
the following capabilities:

```js
{
  product: "PersonaMonkey Route Manager",
  productVersion: "0.8.0",
  protocolVersion: 1,
  personaApiVersion: "0.7",
  stateSchemaVersion: 2,
  bootId: "...",
  revision: 42,
  capabilities: [
    "personas", "persona-storage", "routes", "workflows",
    "workflow-jobs", "batch", "events", "diagnostics"
  ]
}
```

`system.status` provides the secret-safe operational/security summary. No
external transport capability is advertised in v0.8.0.

The registry is explicit; it never invokes caller-provided namespace/method
strings. Each entry declares its handler, capability, whether it mutates,
whether it is batchable, and whether it is destructive. v1 command families
are:

```text
system.describe                 system.status
persona.list                    persona.get
persona.create                  persona.open
persona.updateIdentity          persona.clone
persona.archive                 persona.destroy
storage.inspect                 storage.clearCookies
storage.clearSiteData           storage.fullWipe
route.list                      route.get
route.assign                    route.test
workflow.list                   workflow.get
workflow.run                    workflow.jobs.list
workflow.jobs.get               workflow.jobs.stop
workflow.jobs.clearFinished     batch.execute
```

Portable Persona import/export may remain on the Persona API in v1 if safe
binary transport and explicit sensitive-cookie choices are not ready. If added,
both request and archive limits must be enforced and sensitive data must always
require explicit intent.

The v0.7 facade remains compatible. v0.8 adds `PersonaManager.updateIdentity`
and normalizes the existing open operation where needed. `WorkflowRunner` is
extended by reusing the existing orchestrator for `list`, `get`, `run`,
`listJobs`, `getJob`, `stopJob`, and `clearFinishedJobs`; public job views stay
redacted. `Diagnostics` gains explicit system/persona/route status methods
while preserving `getStatus` as a compatibility alias.

`RouteManager` is an additive facade with `list`, `get`, `assign`, and `test`.
It returns a redacted route inventory and delegates assignment/testing to the
existing profile-route and route-test logic. Block is always assignable;
missing or disabled routes fail safely; Direct requires `allowDirect: true`.
Route credential creation/editing/deletion is not extracted for this release.

## State consistency and revisions

The state manager provides a small serialized mutation primitive:

```js
stateManager.getRevision()
stateManager.mutate(mutator, { expectedRevision })
```

Mutations execute through one internal queue. Each mutator receives an
isolated current-state draft; its committed draft is sanitized with existing
cross-reference integrity logic before persistence. A commit advances the
monotonic runtime `revision` only after persistence succeeds and returns a
stable `{ state, result, revision }`-style result. `getState` and `setState`
remain available for v0.7 compatibility.

`expectedRevision` is optional optimistic concurrency control. A mismatch
rejects with `STATE_CONFLICT` before mutation. Failed mutations and failed
persists do not advance the revision. A process-lifetime revision is sufficient
because every response/event also carries a runtime-unique `bootId`; clients
must refresh after a boot change. This bookkeeping does not require a persisted
state schema bump.

State-change subscribers are added without removing the current privacy
controller hook. Subscriber failures are isolated and cannot fail a committed
mutation. PCMS-exposed mutations—including persona creation/identity/clone/
archive/destroy/wipe/import and route assignment—must use the primitive so
independent read-modify-write cycles cannot lose each other's updates.

## Batch policy

`batch.execute` accepts one registered batchable command plus an explicit,
deduplicated ordered list of persona IDs:

```js
{
  command: "route.test",
  personaIds: ["persona-a", "persona-b"],
  params: {},
  concurrency: 4,
  failurePolicy: "continue"
}
```

Initial bounds: at most **200** selected personas, default concurrency **4**,
and maximum concurrency **16**. Result rows retain first-occurrence input
order, including an error row for missing or unmanaged personas. The supported
failure policies are `continue` and `failFast`; `failFast` prevents scheduling
new work after the first failure but preserves completed rows and reports a
clear outcome for unscheduled IDs. One item's error must not modify another
persona.

Only commands explicitly marked batchable may run: initially `persona.open`,
`route.test`, `route.assign`, and selected read/status operations if useful.
`persona.destroy`, `storage.fullWipe`, `storage.clearCookies`,
`storage.clearSiteData`, and sensitive import/export are non-batchable in
v0.8.0. Single-target destructive commands require explicit intent/confirmation
as defined by their registry metadata; they never become accidental defaults.

## Events and UI client

The extension-internal event transport is a WebExtension runtime Port named
`PCMS_EVENTS`. It is not a network endpoint. Events are advisory: queries are
the source of truth and the client refreshes after reconnect, a sequence gap,
or a changed `bootId`.

```js
{
  version: 1,
  bootId: "...",
  sequence: 18,
  revision: 42,
  at: "2026-09-15T00:00:00.000Z",
  type: "route.assignment.changed",
  entity: "persona",
  entityId: "persona-a",
  data: {}
}
```

`sequence` is runtime-local and strictly increasing. Payloads are bounded and
sanitized, subscribers are removed on port disconnect, and a broken subscriber
cannot break a mutation. Coarse event types are `state.changed`,
`persona.changed`, `persona.removed`, `route.assignment.changed`,
`route.test.completed`, `workflow.job.changed`, `workflow.job.finished`, and
`pcms.batch.completed`. Workflow events are produced through the existing
orchestrator lifecycle rather than high-frequency history polling.

The dedicated console lives in `extension/pcms/` (`index.html`, `pcms.js`, and
`pcms.css`) and uses `pcms-client.js`/PCMS commands exclusively for Persona
management. It does not call contextual-identities, cookies, browsing-data,
proxy, or local-persistence APIs and does not send raw-state mutations. It
offers an overview, responsive multi-select persona operations (safe route
test/assignment), workflow-job views and stopping, and an in-memory activity
feed capped at **500** rows. Detailed cookie/storage/package/backup/userscript/
workflow-authoring/diagnostics editors remain in their established screens.

## Transport boundary and explicit non-goals

v0.8.0 supports internal browser runtime messaging only. The protocol is
transport-neutral so a later, separate local adapter can forward its explicit
registry. That adapter would require opt-in, authenticated or OS
permission-controlled local-only transport, strict command allowlisting,
request-size bounds, and secret-free responses. v0.8 does not add TCP, HTTP,
WebSocket, Internet/cloud control, or a generic native-host server.

Also out of scope: persistent groups/tags, scheduling/cron, a second workflow
engine or DAG redesign, multi-machine orchestration, arbitrary RPC/plugins/
JavaScript execution, raw browser API/state-editor access, route credential
management redesign, a wholesale options-page rewrite, unsafe cross-container
site-storage copying, a new backup format, and browser-profile synchronization
beyond existing recovery behavior.

## Release acceptance criteria

The milestone is ready only when:

1. Protocol v1, capability discovery, explicit command registry, secret-safe
   structured errors, revision metadata, bounded batches, and runtime events
   are documented and implemented through the Persona OS facade.
2. State manager tests cover serialization, revision success/conflict/failure,
   subscriber isolation, and cross-reference sanitation; PCMS mutation paths
   demonstrate no lost update under concurrent calls.
3. Protocol, facade, route-redaction/Direct-opt-in, batch, and event tests
   cover their stated bounds and safety behavior, including workflow job
   transitions and no serialized stack traces/secrets.
4. A deterministic PCMS browser smoke test proves the console boots, renders
   description/personas/jobs, performs selection, route assignment/testing and
   job stopping, handles events, and renders errors without breaking. Existing
   browser and extension security/isolation tests continue to pass.
5. Documentation (`README.md`, `DEVELOPMENT.md`, `docs/PERSONA_OS_API.md`,
   `docs/PCMS_API.md`, and release notes) matches the shipped API; version
   metadata is bumped only at the coherent release checkpoint.
6. `npm run release:check` passes to the extent the environment supports it;
   unavailable browser/installed Firefox/LibreWolf/native-routing E2E checks
   are reported as unverified, never claimed as passed.
7. The final diff/status is reviewed, generated artifacts and private material
   are absent, v0.7 compatibility/security invariants remain intact, and work
   is committed in coherent checkpoints.

## Deferred follow-up

v0.8.1+ may consider an opt-in local adapter, cancellation composition for
batches, deliberately designed destructive bulk confirmation, and any broader
management/editor extraction only after the v1 boundary has proven stable.
